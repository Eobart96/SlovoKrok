# Project agent instructions

## Start

Локальный single-user SlovoKrok (Slovak A1): Next.js/React/TypeScript +
FastAPI/SQLAlchemy/SQLite + Codex/OpenAI-compatible tutor. Текущая цель — в
`PROJECT_CHECKPOINT.md`; auth, multi-user, PostgreSQL, микросервисы и deployment
не добавлять без явного запроса.

1. Выполни `git status --short`; не откатывай существующие изменения.
2. Прочитай `PROJECT_CHECKPOINT.md` и проследи затронутый runtime path.
3. Открой только нужную строку маршрутизации ниже.

Не загружай целиком `PROJECT_REPORT.md`, `PROJECT_HISTORY.md`, `CHANGELOG.md`,
`ROADMAP.md`, `.ai/*.md` или весь `docs/` для обычной задачи.

## Модели, субагенты и уровень размышления

Эта политика направляет выбор модели, но не является технической блокировкой.
Сначала оцени связность, риск и объём передачи контекста. При создании субагента
явно выбирай указанную модель и `reasoning_effort`, если они доступны в текущей
подписке и интерфейсе Codex; недоступную комбинацию не подменяй молча.

### Sol (`gpt-5.6-sol`)

Назначай Sol задачи, где важны глубокий анализ, широкий контекст или независимое
ревью:

- архитектура и анализ требований, особенно границы Browser → Next.js → FastAPI
  → SQLite и Codex CLI/OpenAI-compatible provider;
- диагностика сложных или непостоянных ошибок: hydration/localStorage,
  синхронизация прогресса, транзакции/backup SQLite, сетевые retry, Playwright
  focus/selection и provider JSON;
- безопасность: `.env`/API keys, локальный Codex CLI bridge, валидация
  недоверенного AI output, backup import и сохранность пользовательских данных;
- изменения в нескольких слоях или модулях, например `CourseState` + Pydantic
  schema/API + `frontend/app/lib/api.ts` + UI + тесты/документация, а также
  SQLite, backup/restore и другие изменения пользовательских данных;
- планирование рефакторинга `CourseScreen`, hooks/data engine, backend routers и
  services, а также итоговое ревью реализации.

### Terra (`gpt-5.6-terra`)

Назначай Terra небольшие изолированные задачи с уже понятным результатом:

- точечные правки текста, документации или одного lesson-файла без смены slug,
  activity ID, структуры курса и проверочной логики;
- форматирование, локальные переименования и механические однотипные изменения
  по явно заданному шаблону;
- простые UI/CSS-изменения в одном компоненте без нового состояния, API или
  browser-storage contract;
- реализация локальной части уже утверждённого плана без новых архитектурных
  решений;
- написание или локальное исправление целевого теста при заранее подтверждённом
  поведении.

### Luna (`gpt-5.6-luna`)

Назначай Luna массовые, однотипные и легко проверяемые задачи с точной
инструкцией, без самостоятельных решений:

- поиск файлов, символов и ссылок через `rg`, инвентаризация структуры и сбор
  фактов без архитектурных выводов;
- проверка наличия путей, повторов, пропущенных lesson-файлов и других явно
  заданных инвариантов без изменения файлов;
- запуск заранее выбранной целевой проверки, например одного pytest-файла,
  `npm.cmd run validate:a1` или узкого Playwright `--grep`, и краткая передача
  фактического вывода текущему агенту;
- механическая сводка уже полученных логов или результатов по заданному формату.

Luna не меняет логику, публичный API, схему данных, авторизацию, безопасность
или файлы конфигурации; ей также не поручаются самостоятельный выбор исправления
и лингвистическая проверка словацкого материала. Если Luna предлагает изменения,
Terra применяет их по готовому списку, а Sol проверяет результат только при
существенном влиянии на проект.

### Уровень размышления

Начинай с наименьшего достаточного уровня и повышай его только из-за реально
обнаруженной сложности или риска:

- **Terra + low** — механическая очевидная правка в одном изолированном месте:
  текст, CSS, локальное переименование или замена по точному шаблону.
- **Terra + medium** — небольшая логика по готовому плану либо написание
  целевого pytest/Playwright-теста для уже подтверждённого поведения.
- **Sol + medium** — обычный анализ требований, планирование, диагностика и
  ревью, например прослеживание потока `CourseScreen` → hook → `api.ts`.
- **Sol + high** — безопасность, API и пользовательские данные, `CourseState`,
  Pydantic/SQLite/backup, несколько модулей, сложная ошибка или рефакторинг.
- **Sol + xhigh** — только исключительная задача с высоким риском либо
  независимая финальная проверка критичного изменения данных или безопасности.
- **Luna + low** — массовые, однотипные и легко проверяемые задачи без
  самостоятельных решений; если этого мало, выбирай Terra или Sol, а не
  повышай уровень Luna.

Не используй `high` или `xhigh` для простой задачи. Если в ходе работы границы
расширились, останови узкого субагента и заново выбери модель и уровень.

### Правила выбора и проверки

- При подходящем качестве выбирай более дешёвого субагента, если это снижает
  расход лимита или токенов, даже когда передача контекста и выполнение займут
  больше времени. Не делегируй, если это не экономит лимит и не повышает
  качество.
- Если задача пересекает стабильные контракты (`CourseState`, API, SQLite,
  browser-storage keys, slug/activity ID), пользовательские данные, AI/security
  boundary или несколько компонентов/слоёв, выбирай Sol.
- Если Terra затронула логику, публичный API, данные, авторизацию, безопасность
  или несколько компонентов, результат до принятия обязательно проверяет Sol.
- Модель и `reasoning_effort` выбираются вручную при каждом запуске субагента:
  Sol для сложной работы и ревью повышенного риска, Terra для изолированной
  реализации, Luna для массовых однотипных задач и запуска заранее выбранных
  проверок. При достаточном качестве экономия лимита важнее скорости выполнения.

## Context routing

- UI/state: `frontend/app/page.tsx`, `components/CourseScreen.tsx`, `data/`.
- Lesson content: нужный `data/modules/.../lessons/<slug>.ts` и
  `docs/COURSE_FORMAT.md`.
- API/storage: `frontend/app/lib/api.ts`, нужный backend router/schema/service;
  `docs/API.md` или `docs/DATABASE.md` только при изменении контракта.
- Tutor: `backend/app/tutor.py`, `routers/tutor.py`, `docs/AI_SYSTEM.md`.
- Cross-layer architecture: `docs/ARCHITECTURE.md`; проверки: `docs/TESTING.md`.

## Contracts and safety

- Course content живёт во frontend; SQLite хранит состояние. Frontend API —
  только через `frontend/app/lib/api.ts`.
- Slug, activity ID, `CourseState`, browser-storage keys, API URL и физические
  SQLite table names не менять без compatibility/migration плана.
- AI output недоверенный и валидируется Pydantic; SQLite reads не должны писать.
- Не читать/публиковать `.env`, credentials, `.ai/private/`, `backend/data/`.
- Не удалять/мигрировать SQLite и не очищать `del/`, `_git-package/`, `.git`;
  commit/push/PR/release — только по явному разрешению.

## Checkpoint discipline

`PROJECT_CHECKPOINT.md` — только актуальная точка продолжения, не changelog,
дневник сессий и не архив выполненных планов.

- Обновляй существующие разделы на месте; не добавляй датированные записи в
  конец файла и не дублируй уже записанное состояние.
- Оставляй только: текущее состояние, последние существенные изменения,
  последний подтверждённый набор проверок, открытые риски, приоритетные задачи
  и точную следующую точку продолжения.
- Завершённые задачи удаляй или сворачивай в одну строку текущего состояния.
  Не сохраняй пошаговую хронологию, длинные списки файлов, сырой вывод команд,
  старые результаты проверок и повторные версии одного плана.
- Держи файл не больше **250 строк и 20 КБ**. Если обновление превышает любой
  лимит, в той же задаче сначала удали устаревшее и объедини повторяющееся.
- План исправлений держи приоритетным и компактным: не более 10 верхнеуровневых
  задач, по 1–3 коротких пункта на задачу.
- Маленькая правка без изменения точки продолжения не требует обновления
  checkpoint.

## Execution history

`PROJECT_HISTORY.md` — общая история для владельца и write-only архив для
агента. Она пополняется автоматически, но не входит в рабочий контекст.

- Не открывай, не читай, не пересказывай и не ищи по старым записям этого файла
  при старте, аудите или обычной задаче. Прочитать историю можно только по
  прямому запросу владельца именно на чтение или анализ истории.
- После каждого существенного и проверенного этапа без отдельной просьбы добавь
  новую запись сразу под маркером `<!-- AGENT_APPEND_HERE -->`. Сам маркер
  оставь на месте; остальную часть файла перед записью не читай.
- Вставляй запись точечным `apply_patch`, заменяя только строку маркера на этот
  же маркер и новый блок. Не загружай файл целиком для поиска места вставки.
- Запись содержит дату, краткий результат, подтверждённые проверки и важное
  ограничение; максимум 5 коротких пунктов. Не добавляй сырые логи, списки
  файлов, секреты, незавершённые попытки и повтор уже существующей записи.
- Мелкие правки текста или служебных правил отдельно в историю не записывай.
  Если они завершают заметный этап, объедини их с итоговой записью этапа.

## Done

Минимально проверь затронутый слой по `docs/TESTING.md`. Перед завершением:
repository audit, `git diff --check`, `git status --short`. Обновляй только
`PROJECT_CHECKPOINT.md`, если изменилась точка продолжения; после обновления
проверь его лимиты. Существенный завершённый этап автоматически запиши в
`PROJECT_HISTORY.md` без чтения накопленной истории. Большой report — лишь по
отдельному checkpoint-запросу.

- **UI-тесты не запускать без явного запроса владельца.** Это относится к
  Playwright, `npm.cmd run test:ui`, любым UI-gate/браузерным сценариям и
  точечным UI-тестам. Не считать их обязательной проверкой по умолчанию и не
  поручать субагентам; при необходимости указать в итоге, что они не запускались
  по этому постоянному правилу. Запуск разрешён только когда владелец прямо
  попросил выполнить UI-тесты в текущем запросе.

- Финальное ручное тестирование и приёмку интерфейса выполняет владелец проекта;
  Codex не объявляет UI окончательно принятым, но может запускать автоматические
  и целевые технические проверки, кроме UI-тестов по правилу выше.
