# База данных

Локальная база по умолчанию на Windows:
`%LOCALAPPDATA%\SlovoKrok\app.db`. На macOS используется
`~/Library/Application Support/SlovoKrok`, на Linux —
`$XDG_DATA_HOME/slovokrok` либо `~/.local/share/slovokrok`.

Абсолютный `SLOVOKROK_DATA_DIR` меняет общую папку runtime data. Явный внешний
`DATABASE_URL` имеет приоритет только для БД; AI settings и launcher продолжают
использовать data root. SQLite URL внутри репозитория считается legacy-путём:
его файл копируется в data root, а runtime использует локальную копию.

При первом запуске существующий `backend/data/app.db` копируется стандартным
SQLite backup API только если нового `app.db` ещё нет. До публикации копии
проверяются `PRAGMA quick_check` и совпадение числа страниц. Legacy-БД не
изменяется и не удаляется; существующая новая БД никогда не перезаписывается.

Rollback БД: остановить приложение, указать абсолютный legacy `DATABASE_URL` и
явно установить `SLOVOKROK_ALLOW_PROJECT_DATABASE=true`, затем снова запустить.
Для возврата старых AI settings можно отдельно направить
`SLOVOKROK_DATA_DIR` на каталог с их legacy-копией. Этот режим вновь хранит
runtime data в синхронизируемом проекте и предназначен только для временного
восстановления. Перед ручной заменой любого файла следует сохранить обе версии.

Модели приложения называются `Course*`. Для совместимости с уже сохранённым
прогрессом они пока используют прежние физические имена таблиц:

- `module1_beta_state`;
- `module1_beta_exercises`, `module1_beta_exercise_attempts`;
- `module1_beta_readings`, `module1_beta_reading_attempts`;
- `module1_beta_vocabulary`;
- `module1_beta_homework`, `module1_beta_homework_attempts`.

История переводчика использует отдельные физические таблицы
`translator_history` и `translator_history_questions`; API удаляет связанные
вопросы перед удалением перевода. Backup format v2 включает обе таблицы;
format v1 остаётся совместимым и трактует их как пустые.

Версии структуры записываются в служебной таблице
`slovokrok_schema_migrations`. Startup проверяет известную непрерывную историю,
создаёт рядом с непустой runtime-БД проверенную копию вида
`app.db.pre-migration-vN-to-vM.bak`, а затем применяет все ожидающие миграции в
одной транзакции `BEGIN IMMEDIATE`. Первая миграция создаёт отсутствующие
активные таблицы через SQLAlchemy `create_all`; она не удаляет дополнительные
classic-таблицы. При неизвестной истории, ошибке `quick_check` или сбое миграции
startup останавливается, а транзакция откатывается. Повторный запуск безопасен.

Каждое SQLite-соединение включает `foreign_keys` и `busy_timeout=5000`.
Файловая runtime-БД переводится в WAL только во время startup, до миграций;
обычное открытие read-соединения само по себе journal mode не меняет. Эти
действия относятся только к runtime-копии: найденный legacy-файл не открывается
миграционным runner на запись и остаётся неизменным.

`module1_beta_state.schema_version` описывает JSON-контракт состояния. Версия 1
по-прежнему читается с совместимыми значениями по умолчанию; следующая запись
нормализует её в версию 2. Новая колонка для optimistic concurrency не нужна:
opaque revision вычисляется из версии схемы, времени обновления и точного JSON,
а SQL `UPDATE` сравнивает прежние значения атомарно. Поэтому существующая SQLite
открывается без DDL-изменения, а устаревший клиент получает конфликт вместо
перезаписи более нового прогресса.

Любое физическое удаление старых таблиц требует отдельной миграции, резервной
копии, явного согласия владельца и тестов на старой/новой базе. Alembic пока не
введён: локальный versioned runner намеренно покрывает текущую небольшую
single-user схему.
