общие файлы затронуты несколькими этапами, поэтому простое разделение по папкам
может разорвать совместимый контракт. Разделять их следует по hunks после review.

## Точный состав

Из корня проекта:

```powershell
node scripts/git-candidate.mjs --self-test
node scripts/git-candidate.mjs --write
node scripts/git-candidate.mjs --verify tmp/git-candidates/<имя-из-вывода>.json
```

Последняя команда должна вернуть `missing=0 extra=0 hash_mismatches=0` и
`GIT_CANDIDATE_OK`. Manifest содержит только пути, размеры и контрольные суммы,
а не личные данные или содержимое файлов. После дальнейшей правки или принятия
нового коммита нужен новый manifest и соответствующая повторная проверка.

## Итоговый review перед локальным коммитом

Прослежены сохранение прогресса и условное обновление по предыдущей revision,
backup с переназначением связей и rollback, tasks-only export/import и
перечитывание после потерянного POST/DELETE-ответа. Нового подтверждённого
дефекта, требующего исправления до локального коммита, не выявлено.
Это не построчное ревью всех накопленных изменений и не ручная приёмка UI.

Границы восстановления после сетевого сбоя:

- `recoverGeneratedItem` сопоставляет тему и ID, отсутствующие в исходном списке.
  При параллельной генерации или устаревшем списке этого недостаточно для точной
  корреляции. Возможное дальнейшее улучшение — явный ID запроса с совместимостью.
- После потерянного ответа общего DELETE число попыток восстанавливается по
  `latest_attempt`: это не полное число всех удалённых попыток. Текущий интерфейс
  показывает число заданий, но будущим потребителям нельзя обещать точный счётчик.

Из-за переплетённых изменений безопаснее сохранить согласованный проверенный
пакет одним локальным коммитом. Три группы выше — ориентир для будущих независимых
задач, а не готовое разделение текущего diff.
